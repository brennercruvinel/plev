# task-102: reusable builds and web commands

The work reduced recompilations caused by different feature sets and gathered
the commands to run the web targets.

## Dependencies

`rust/unions`, generated by cargo-hakari, requests the union of the features used
by the workspace members on the configured targets: macOS and Linux; wasm is left
out (`.config/hakari.toml`, lines 21 to 27). `proc-macro2` is excluded:
`span-locations`, which enables the engine's hot reload (`rust/engine/Cargo.toml`,
lines 35 to 43), must not be copied into the build of the macros
(`.config/hakari.toml`, lines 29 to 37). In the measurement at `540e218d`, each
member recompiled crates already compiled in the workspace: 54 for `-p arcade`,
65 for `-p uigallery` and 7 for `-p commit`; after the union, zero in each case.

The development profile also limits debug information: line tables for local
code and none for dependencies (`Cargo.toml`, lines 164 to 175). Measured at
`706dfa82`, with `cargo test -p engine --no-run` on a clean target on an M-series
Mac, the time went from 96 s and 3.8 GB to 85 s and 2.1 GB. See
[ADR 0083](../../adr/workflows/0083-feature-unification.md).

## Web execution

`webtarget.sh` points trunk at each target's folder (`apps/uigallery/web`,
`apps/urnadbapp/web`, `demo/graphs` and `demo/primes`), where `Trunk.toml` and
`index.html` are located, and accepts `uigallery`, `urnadbapp`, `graphs` or
`primes` (`tool/tasks/webtarget.sh`, lines 22 to 27). In `serve`, it starts at the
target's port (8080 to 8083) and looks for the next free one, up to 50 ports
above; an explicit `--port` takes precedence. The `build` mode forwards the
arguments without looking for ports (lines 45 to 61).

The explorer recovered its own web binary (`62cb40e8`), and the README commands
now show executable lines (`f57c9054`, `229f046b`). Code:
[tool/tasks/webtarget.sh](https://github.com/brennercruvinel/plev/blob/ec0a224c2d6c5a446e70cf4ca9ee92fd66eef713/tool/tasks/webtarget.sh)
and [.config/hakari.toml](https://github.com/brennercruvinel/plev/blob/ec0a224c2d6c5a446e70cf4ca9ee92fd66eef713/.config/hakari.toml).

## Rust lessons

Building one package and building the workspace can enable different features of
the same dependencies, and each variant becomes one more artifact in `target/`
(`540e218d`). The unification configuration must respect the separation between
host, proc-macro and target dependencies: copying the `span-locations` feature to
the host would make each `Span` in `rust/macros` grow (`.config/hakari.toml`,
lines 29 to 33).
