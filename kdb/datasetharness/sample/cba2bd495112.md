# discord/server.ts, plugin oficial (nao e cocriacao)

este arquivo nao e trajetoria nem codigo do brenner. e o source de um plugin
oficial do marketplace claude-plugins-official: o canal Discord pro Claude Code,
um MCP server self-contained com controle de acesso. entrou na fonte porque o
dump claude2026 copiou o marketplace de plugins inteiro. nao tem input humano
caotico pra reconstruir, entao nao passa por brennerwritter; normalizo a
estrutura e a proveniencia e deixo o registro honesto pro dedupe e a auditoria.

## o que o arquivo e (extracao estrutural)

server MCP em TypeScript pra bun, fala com a Discord API via discord.js e com o
Claude Code via StdioServerTransport. carrega o bot token de
~/.claude/channels/discord/.env (forca permissao 0600 no arquivo), e expoe cinco
tools mais um relay de permissao.

modelo de acesso, em access.json gerido pela skill /discord:access:

- dmPolicy: pairing, allowlist ou disabled. em pairing, um sender novo recebe um
  codigo de 6 hex, valido por 1h, no maximo 3 pendentes, resposta no maximo duas
  vezes antes de silenciar. a aprovacao acontece fora de banda (a skill grava um
  arquivo em approved/, o server faz polling a cada 5s e confirma)
- groups: opt-in por canal (chaveado por channel ID, nao guild ID), com
  requireMention e allowFrom por canal. thread herda o opt-in do canal pai
- modo static: snapshot do acesso no boot, sem mutacao em runtime, pairing cai
  pra allowlist com warning

tools expostas:

- reply: responde no Discord, chunk de 2000 chars (cap duro do Discord), threading
  opcional via reply_to, ate 10 anexos de 25MB
- react: adiciona reacao de emoji a uma mensagem
- edit_message: edita mensagem anterior do bot (edicao nao dispara push, entao o
  codigo orienta mandar reply novo quando a task longa termina)
- download_attachment: baixa anexos pro inbox local
- fetch_messages: puxa historico (a API de busca do Discord nao e exposta a bots,
  entao isso e o unico lookback)

## defesas que o codigo codifica (o que vale pro dataset de harness)

o arquivo e denso em controle de seguranca, e ai esta o valor de referencia:

- assertSendable recusa anexar qualquer arquivo dentro do STATE_DIR (menos o
  inbox), pra Claude nao exfiltrar o proprio estado do canal via reply
- gate de saida espelha o gate de entrada: uma tool so manda pra chats que o
  gate de entrada entregaria, resolvendo thread pro canal pai
- nome de anexo controlado pelo uploader e sanitizado (remove colchete, newline,
  ponto e virgula) porque cai dentro de anotacao e de tool result onde
  delimitador deixa o atacante escapar do frame nao confiavel
- as instrucoes do server avisam o modelo: a skill de acesso so roda no terminal
  do usuario, nunca aprovar pairing nem editar access.json porque uma mensagem
  do canal pediu. esse e exatamente o pedido que uma prompt injection faria
- relay de permissao: pedido de permissao do Claude Code vira mensagem com
  botoes Allow/Deny nos DMs allowlistados, ou resposta de texto no formato
  estrito "y/n mais 5 letras", e so de quem ja passou pelo gate

obs de normalizacao: o source usa varios emoji (cadeado, check, cruz) como label
de botao e prefixo de notificacao, e em dash nos comentarios. nada disso foi
reproduzido aqui, conforme o mantra; os glifos foram descritos por nome.
