> # plev
> 
> ## abstract
> 
> **plev: um motor de compositing gpu unificado para targets nativos e web a partir de um único codebase rust**
> 
> a fronteira entre renderização nativa e renderização web não é consequência de constrangimento físico. é um acidente histórico. essa distinção importa porque muda fundamentalmente o que se torna possível: se a separação é acidental, ela é eliminável, e sua eliminação é agora realizável dentro das garantias de memória segura e abstrações de custo zero de uma linguagem de sistemas operando no momento exato de maturidade da padronização webgpu.
> 
> apresentamos plev, um motor de compositing gpu-first implementado em rust que dissolve essa dicotomia no nível de compilação, não no nível de abstração. o mesmo codebase não modificado compila para metal em macos e ios, vulkan em linux e android, direct3d 12 em windows, e webgpu no browser via wasm32-unknown-unknown, com execução de shaders idêntica em todos os targets. nenhum framework existente propõe isso sem degradar ao menos um dos lados: abstrações que sacrificam fidelidade de renderização na web, ou codebases bifurcados que garantem divergência comportamental ao longo do tempo.
> 
> o modelo de compositing é dirigido por scene graph regenerado integralmente por frame, evitando deliberadamente tanto reconciliação de virtual dom quanto diffing de retained mode tradicional, em favor de um compositor que raciocina diretamente sobre estado de gpu. dirty region tracking garante que apenas regiões de cena mutadas geram submissões à gpu por frame, propriedade atualmente ausente em todos os competidores baseados em wgpu, incluindo iced e egui. renderização de texto, historicamente o ponto de falha decisivo de todo framework rust direcionado a webassembly, é resolvida através de uma arquitetura de atlas de glifos residente em gpu construída sobre cosmic-text e harfbuzz, entregando shaping unicode de qualidade de produção, layout bidirecional, suporte a ligatures e fidelidade subpixel equivalente à de editores nativos como zed e sublime text, sem rasterização cpu por frame para regiões de texto estável.
> 
> o timing não é incidental. webgpu atingiu suporte estável em todos os browsers principais em 2024 e maturidade cross-platform completa incluindo safari e ios em 2026, representando o primeiro intervalo em que essa arquitetura é fisicamente realizável sem degradação. quem tentar isso em 2027 encontrará um ecossistema estabelecido.
> 
> até onde é de nosso conhecimento, plev constitui o primeiro motor de compositing a entregar semântica uniforme, shaders idênticos, atlas de glifos em gpu, dirty tracking e compositing de camadas independentes nos seis targets principais a partir de uma única unidade de compilação. a implicação não é apenas técnica: é que décadas de duplicação de esforço, abstrações degradantes e codebases bifurcados foram escolhas, não inevitabilidades, e que desfazê-las é agora o trabalho de um codebase, não de uma geração.
> 
> ---
> 
> ## 1. o que é o plev
> 
> tecnicamente o plev é um **compositing engine**. não é um framework de widgets. não é um runtime reativo. é a camada que transforma descrições de cenas em draw calls na gpu, e que faz isso de forma idêntica independente de estar rodando sobre vulkan, metal, dx12 via wgpu-native, ou sobre webgpu via wgpu no browser.
> 
> o modelo central é um scene graph gerado por rust puro a cada frame, não reconciliado como virtual dom, não diffado como retained mode tradicional. cada frame descreve o que existe, o compositor decide o que mudar na gpu. isso elimina a categoria inteira de bugs de estado inconsistente entre ui e dado.
> 
> o que o plev unifica que ninguém unificou ainda: o atlas, o compositor, o scene graph, o event system - tudo isso é o mesmo código rust compilado para `wasm32-unknown-unknown` com backend webgpu, ou para `x86_64`/`aarch64` com backend nativo. não é abstração em cima de dois renderers diferentes. é um renderer com dois targets de compilação.
> 
> ---
> 
> ## 2. o problema - o gap que o plev resolve
> 
> todo framework existente trata web e nativo como alvos separados com codebases separadas ou abstrações que degradam os dois. o que não existe é um modelo de compositing unificado que compila para wgpu-native e wgpu-web sem concessões, onde a ui rodando no mac e rodando no browser de outro usuário é literalmente o mesmo binário rust compilado para targets diferentes.
> 
> a questão técnica central é **text rendering** - é onde todo framework rust-para-wasm falha. a resposta correta é cosmic-text para shaping e layout de texto, renderizado via wgpu com atlas de glifos na gpu. isso é o que separa um experimento de algo real.
> 
> o gap é verificável:
> - egui existe há anos e o text rendering ainda é visivelmente inferior a qualquer ui nativa
> - slint é retained mode tradicional
> - leptos e dioxus são react em rust
> - ninguém resolveu o problema unificado nativo + web com qualidade de produção
> 
> isso não é opinião, é o estado documentado do ecossistema.
> 
> a demanda está chegando antes do supply. zed, warp, linear, ferramentas de dev tools estão todas migrando para gpu-accelerated ui. o próximo passo natural é esse modelo rodando no browser sem reescrever nada. plev seria a resposta antes que a pergunta se torne mainstream.
> 
> ---

> ## 3. targets de plataforma
> 
> plev é o primeiro nativo para 6 targets a partir de um único codebase:
> 
> | plataforma | gpu backend |
> |----------------|-------------|
> | macos | metal |
> | ios | metal |
> | linux | vulkan |
> | android | vulkan |
> | windows | dx12 |
> | browser (wasm) | webgpu |
> 
> o mesmo renderer, os mesmos shaders, compilados para targets diferentes. flutter faz algo conceitualmente similar com skia/impeller mas em dart, sem webgpu real, e com renderer separado para web. o plev seria a primeira resposta em rust com qualidade de produção para todos esses targets simultaneamente.
> 
> **trabalho adicional real para mobile:** input, touch, gestures, ime para teclado virtual, safe areas, lifecycle de app (background/foreground). winit já tem suporte a android via `android-activity` crate e ios via `objc2`. não é trivial mas é mapeado.

> ## 4. arquitetura core
> 
> ### 4.1 gpu-first + hybrid immediate/retained
> 
> - **inspiração principal:** gpui (do zed) + iced + cosmic-text, mas unificado e melhorado
> - **modelo:** hybrid mode (como gpui) - immediate para partes dinâmicas/reativas, retained para camadas estáveis (ex.: toolbars, sidebars). scene graph regenerado por frame, mas com dirty region tracking agressivo + layer caching na gpu (só re-renderiza o que mudou, como no gpui, mas com suporte full a blur, shadows, opacity groups)
> - **backend:** wgpu puro (webgpu nativo + wgpu-native). mesmos shaders wgsl compilados para todos os targets. sem abstrações degradantes, performance idêntica em native e web
> 
> por que isso ganha do flutter? flutter usa impeller (skia → gpu), mas ainda tem overhead no web (canvas/webgl fallback em alguns casos). aqui é webgpu real, shaders idênticos, sem perda de fidelidade.
> 
> ### 4.2 text rendering - nível editor nativo (zed/sublime/vs code)
> 
> text rendering é o subsistema mais crítico e mais separado. cosmic-text recebe strings unicode, faz shaping via harfbuzz, retorna glifos posicionados. esses glifos vivem num atlas de texturas na gpu - uma textura 2d onde cada glifo ocupa uma região. renderizar texto é desenhar quads mapeados para regiões desse atlas. é o que zed faz, o que sublime faz, o que separa text rendering de qualidade de produção de text rendering de experimento.
> 
> - **base:** cosmic-text + swash (shaping com harfbuzz, layout bidirectional, ligatures, color emoji, subpixel aa)
> - **atlas de glifos na gpu:** dinâmico, com lru eviction, mipmapping para zoom suave, hinting adaptativo. suporte a variable fonts, fallback chains e shaping complexo (árabe, devanagari, etc.)
> - **diferencial:** integração nativa com system fonts (font-kit ou similar) + cache global de atlas. texto renderizado como quads texturizados, zero rasterização cpu por frame em texto estável
> - flutter perde aqui: flutter tem bom texto, mas em web ainda depende de canvas (pior aa/hinting). plev seria visivelmente superior em apps de código, docs, chat, etc.
> 
> ### 4.3 performance
> 
> - **dirty tracking + occlusion culling:** só submete draw calls para regiões alteradas
> - **compute shaders para efeitos:** glow, blur, particle systems, animações físicas - tudo na gpu
> - **mobile-first extras:** safe areas, notch handling, lifecycle (background → foreground), touch gestures nativos via winit + android-activity/objc2
> - **benchmarks target:** apps com 10k+ elementos interativos a 144 fps em hardware médio, startup < 100ms (wgpu é leve)
> 
> ### 4.4 relação com gpui do zed
> 
> plev **não usa** gpui do zed. são filosofias diferentes.
> 
> gpui é o compositor interno do zed. arquiteturalmente acoplado ao zed, macos-first, sem target wasm, sem android, sem ios, não é uma biblioteca pública no sentido real - é um subsistema que o zed abriu mas não foi concebido para ser consumido externamente.
> 
> o plev usa wgpu diretamente como backend de renderização. gpui também usa wgpu internamente, mas o que o zed construiu em cima é a camada de alto nível deles - entities, contexts, o modelo de reatividade deles. não é reaproveitável.
> 
> o plev toma **inspiração filosófica** do gpui: gpu-first, immediate mode com elementos retained onde faz sentido, qualidade de texto como requisito não opcional - mas a implementação é do zero sobre wgpu + cosmic-text + winit.
> 
> a relação é a mesma que existe entre zed e sublime text: um aprendeu com o outro, nenhum reutiliza código do outro.
>

> ## 5. análise competitiva
> 
> ### egui
> immediate mode, compila pra wasm, mas o renderer é baseado em triângulos simples com text rendering via rasterização cpu-side. cada frame re-rasteriza texto que mudou, sem atlas de glifos persistente na gpu. funciona, mas a qualidade visual é visivelmente inferior - antialiasing medíocre, sem hinting correto, sem suporte real a ligatures. o modelo de compositing não tem noção de camadas, transparência ou blur - tudo é pintado flat. é o mais próximo do que o plev faz mas é uma versão de 2018 do problema.
> 
> ### slint
> retained mode com uma dsl proprietária para descrever ui. compila pra nativo e pra wasm mas o renderer é separado para cada target - em nativo usa skia ou femtovg, na web cai pra canvas 2d ou webgl com qualidade degradada. a dsl é o problema fundamental: você não está escrevendo rust, está escrevendo uma linguagem intermediária que limita o que você pode expressar. não tem acesso direto à gpu.
> 
> ### leptos / dioxus
> não são concorrentes reais - são react em rust. virtual dom, reconciliação, hidratação. o modelo mental é web primeiro, nativo como afterthought via webview. não tem renderer próprio, não fala wgpu, não tem compositing. são frameworks de aplicação, não compositing engines.
> 
> ### iced
> o mais arquiteturalmente ambicioso dos existentes. elm architecture, renderer próprio via wgpu, compila pra nativo e wasm. é o mais próximo conceitualmente do plev. o problema é que o text rendering ainda usa glyphon que tem limitações sérias em shaping complexo, e o modelo de compositing não tem suporte a camadas independentes - tudo é re-renderizado quando qualquer coisa muda. sem dirty region tracking real.
> 
> ### gpui (zed)
> é o estado da arte em ui nativa gpu-accelerated em rust. compositor com camadas independentes, text rendering via core-text no mac com fallback, atlas de glifos correto, model de reatividade baseado em entities e contexts que é genuinamente novo. o problema: é nativo apenas, acoplado ao macos primariamente, não tem target wasm, e é arquiteturalmente inseparável do zed - não é uma biblioteca, é um subsistema interno.
> 
> ### tauri / electron
> não são renderers, são shells que embrulham um webview existente. a gpu é usada pelo chromium por baixo, não por você. não tem controle sobre compositing.
> 
> ### bevy
> wgpu cross-platform (games), glyphon/cosmic-text opcional. ótimo para 3d, mas overhead para ui pura. não é ui-focused.
> 
> ### makepad
> shader-based ui framework com live editing e "turtle layout" model. v1.0 lancado em maio 2025. renderiza tudo via shaders customizados (glsl/wgsl), sem dependencia de skia ou similar. cada widget e um shader. suporta wasm. e o competidor mais direto do plev em filosofia (gpu-first, rust, multi-target). limitacoes: layout model nao-convencional (turtle, nao flexbox), ecossistema menor, dsl proprietaria (.live). o diferencial do plev: dirty tracking per-layer, text rendering via cosmic-text (superior ao texto do makepad), e sintaxe verbal (plev_narrate!).
> 
> ### ribir
> framework wgpu-based com foco em simplicidade. menos maduro que os outros. abordagem single-framework (nao compositing engine). relevante como referencia de ergonomia de api.
> 
> ### compose multiplatform (jetbrains)
> kotlin-based, wasm target adicionado recentemente. referencia de arquitetura multi-target em linguagem nao-rust. usa skia internamente. relevante como modelo de como uma empresa grande aborda multi-platform, mas linguagem e ecossistema completamente diferentes.
> 
> ### por que o plev é superior
> 
> egui e iced são os únicos concorrentes honestos:
> - **contra egui:** atlas de glifos persistente na gpu com cosmic-text é objetivamente superior em qualidade de texto, e o modelo de compositing com camadas é superior em expressividade
> - **contra iced:** dirty region tracking correto significa que o plev só re-renderiza o que mudou, iced re-renderiza a cena inteira em muitos casos
> - **contra gpui:** o plev compila pra webgpu - esse é o único diferencial que importa e que nenhum dos outros tem
> 
> o plev não é superior por ter mais features. é superior por resolver o problema correto - um renderer, dois targets, sem concessão em nenhum dos dois - que nenhum dos existentes se propôs a resolver.

> ## 7. viabilidade técnica
> 
> ### pontos fortes
> 
> **wgpu como base:** wgpu é uma abstração madura e portátil sobre webgpu, rodando nativamente em vulkan, metal, dx12 e opengl, e via webgpu/webgl no wasm. isso permite um codebase unificado sem forks. em 2026, wgpu é estável para produção (usado em browsers como firefox/servo/deno e engines como bevy).
> 
> **cosmic-text para texto:** essa biblioteca é pura rust (sem deps de sistema), com shaping avançado via harfbuzz e rendering via swash (suporte a color emoji, ligatures). é usada em produção no cosmic desktop (pop!_os 24.04, lançado em 2025), que é o primeiro de rust em escala. qualidade elogiada: subpixel rendering, antialiasing superior e performance gpu via atlas de glifos (ex.: glyphon integra cosmic-text com wgpu para text 2d). resolve o "problema central" de texto em wasm.
> 
> **multi-plataforma:** winit já suporta android/ios (via crates como `android-activity` e `objc2`), facilitando input (touch, gestures, ime). dirty tracking e camadas independentes são factíveis em wgpu, inspirado em gpui (que usa wgpu internamente).
> 
> **timing perfeito:** webgpu tem suporte total em browsers em 2026 (chrome/edge/firefox/safari, incluindo ios). adoção cresceu 15x desde 2023, com 70% de market share. empresas usam para ai inference, 3d e apps high-perf no browser (ex.: hugging face tooling).
> 
> ### o gap existe?
> 
> parcialmente sim. nenhum engine exato como plev foi encontrado (unificado compositing com foco em dirty tracking e texto premium sem full gui overhead). mas competidores próximos cobrem partes:
> - **iced:** mais próximo conceitualmente. usa wgpu, cosmic-text (desde v0.18), suporta native e web. limitações: re-renderiza cenas inteiras em muitos casos; glyphon tem issues em shaping complexo
> - **egui:** immediate mode, wgpu, wasm. texto cpu-side, aa medíocre
> - **gpui (zed):** estado da arte native, mas acoplado ao zed e sem wasm oficial
> 
> ### inovação do plev
> 
> superior em unificação sem concessões (mesmos shaders/atlas/event system para todos targets) e dirty tracking (ausente em iced/egui). resolve "fragmentação native-web" melhor que abstrações degradadas. seria o primeiro engine rust com qualidade de produção para todos os 6 targets (incluindo mobile) de um único codebase.
>

> ## 8. desafios e armadilhas conhecidas
> 
> > estes são problemas já identificados, testados e mapeados. não cair nessas armadilhas.
> 
> **complexidade do texto na gpu:** atlas de glifos em wgpu é "o problema mais difícil". gerenciar fallback de fonts, bidirectional e shaping complexo exige tuning. cosmic-text mitiga com lru, mas atlas dinâmico pode fragmentar em casos extremos (textos longos/multilíngues). glyphon tem issues reportados em shaping complexo (ex.: árabe/devanagari), mas fixes em 2026 melhoram.
> 
> **mobile extras:** input e lifecycle (background/foreground, safe areas) não são triviais, mesmo com winit. testes em android/ios demandam esforço extra. safe areas e ime virtual exigem custom code.
> 
> **performance overhead:** immediate mode por frame pode ser ineficiente sem otimizações. dirty tracking é essencial - evitar re-submissões desnecessárias à gpu. wgpu no wasm ainda mais lento em compute shaders vs. native (browsers antigos limitam).
> 
> **maturação:** como engine novo, bugs em edge cases (ex.: transparência, blur em camadas) são comuns. wgpu no wasm tem limites (ex.: webgl fallback em <5% browsers).

> ## 9. visão de api futura
> 
> ### api declarativa + reativa com signals
> 
> inspirado em solid.js / leptos / xilem:
> 
> ```rust
> #[component]
> fn counter(cx: scope) -> impl intoview {
>  let (count, set_count) = create_signal(0);
> 
>  div()
>  .flex().center().p(4).bg("bg-gradient-to-r from-blue-500 to-purple-600")
>  .rounded("2xl").shadow("xl").text("white").text_lg()
>  .child(
>  button()
>  .px(6).py(3).bg("white/20").rounded("xl").hover("bg-white/30")
>  .on_click(move |_| set_count.update(|n| *n += 1))
>  .child("count: {count}")
>  )
> }
> ```
> 
> ### sintaxe verbal "prosa-like" (conceitual/revolucionária)
> 
> nenhum framework rust atual tem sintaxe verbal "prosa-like" pra ui com gpu unificação. coisas próximas existem:
> - floem ou ribir: macros declarative, mais "html-ish" ou struct-based
> - dioxus/leptos: rsx!/view! macros que parecem jsx/react
> - iced: elm-style, funcional e clean, mas não verbal
> - fora de rust: jetpack compose (kotlin) ou swiftui são declarative, mas não "narrativas". o inform 7 é único nesse verbalismo pra domínios criativos
> 
> por que isso seria relevante:

> ## 11. título formal (en)
> 
> > **plev: a unified gpu compositing engine for native and web targets via a single rust codebase**
> 
> the fragmentation of graphical user interface rendering across deployment targets represents one of the most consequential and least examined failures of modern systems software. existing frameworks resolve the native-web dichotomy through abstraction layers that systematically degrade rendering fidelity on at least one target, or through bifurcated codebases that impose prohibitive maintenance costs and guarantee behavioral divergence over time. we present plev, a compositing engine written in rust that eliminates this dichotomy at the architectural level by compiling a single, unmodified codebase to platform-native gpu backends - metal on macos and ios, vulkan on linux and android, direct3d 12 on windows - and to webgpu in the browser via wasm32-unknown-unknown, leveraging wgpu as the portable graphics abstraction layer. the compositing model is scene-graph-driven and regenerated per frame, eschewing both virtual dom reconciliation and conventional retained-mode diffing in favor of a compositor that operates directly on gpu state, eliminating an entire class of inconsistencies arising from desynchronized ui and application state. text rendering, historically the critical failure point of rust-based ui frameworks targeting wasm, is resolved through a gpu-resident glyph atlas architecture built over cosmic-text and harfbuzz, providing production-quality unicode shaping, bidirectional layout, and subpixel fidelity equivalent to that of native editors such as zed and sublime text. dirty region tracking ensures that only mutated regions of the scene are re-submitted to the gpu per frame, a property absent from all current wgpu-based competitors. to our knowledge, plev constitutes the first rendering engine to achieve uniform compositing semantics, identical shader execution, and production-quality text rendering across all six major deployment targets from a single compilation unit. the implications extend beyond tooling: plev establishes that the native-web rendering boundary is an artifact of historical accident rather than physical necessity, and that its dissolution is now achievable within the constraints of a memory-safe, systems-level language at the current moment of webgpu standardization maturity.

> ## pattern 1: analytical spring solver (pre-computed coefficients)
> 
> **source**: natura, `/users/<user>/dev/bc/bunker/repos/web-frontend/animation/natura/natura/src/spring.rs`, lines 73-271

> **description**: natura's spring does not use euler integration. instead, it pre-computes four coefficients (`pos_pos_coef`, `pos_vel_coef`, `vel_pos_coef`, `vel_vel_coef`) based on the analytical solution of the damped harmonic oscillator ode. it handles all three regimes explicitly: under-damped (exp * sin/cos), critically-damped (exp * polynomial), and over-damped (two distinct exponentials). the `update()` call is then just two multiply-add operations -- no branching, no `dt` multiplication, no accumulation error.

> ```rust
> pub fn update(&mut self, pos: f64, vel: f64, equilibrium_pos: f64) -> (f64, f64) {
>  let old_pos = pos - equilibrium_pos;
>  let old_vel = vel;
>  let new_pos = old_pos * self.pos_pos_coef + old_vel * self.pos_vel_coef + equilibrium_pos;
>  let new_vel = old_pos * self.vel_pos_coef + old_vel * self.vel_vel_coef;
>  (new_pos, new_vel)
> }
> ```
> 
> **applicability to plev**: plev's `spring<t>::tick()` uses forward euler integration (`velocity += acceleration * dt; value += velocity * dt`). this has two problems:
> 1. **numerical instability**: with stiff springs or large dt, euler can diverge or oscillate wildly. natura's analytical approach is unconditionally stable for any dt.
> 2. **frame-rate dependency**: euler produces different results at 30fps vs 60fps. the analytical solution gives the exact mathematical answer regardless of timestep.
> 3. **parametrization**: natura uses `angularfrequency` + `dampingratio` (the standard physics parameters) rather than `stiffness`/`damping`/`mass`. the damping ratio directly tells you if the spring is under-damped (<1), critically-damped (=1), or over-damped (>1), which is much more intuitive for designers.
> 
> however, natura's api is 1d-only and requires external state management. plev's `spring<t>` is generic over `springinterpolate` types and self-contained, which is better for the engine's use case. the improvement path is to replace the euler solver internals with the analytical approach while keeping plev's api.
> 
> **decision**: **adapt** -- replace plev's euler integration in `spring<t>::tick()` with pre-computed analytical coefficients. keep the existing `stiffness/damping/mass` api but add a `damping_ratio()` convenience method. this eliminates frame-rate dependence and numerical instability.
>

> ## pattern 2: keyframe sequence with per-segment easing
>

> ## pattern 3: state animator with transition blending
> 
> **source**: mina, `/users/<user>/dev/bc/bunker/repos/web-frontend/animation/mina/core/src/animator.rs`, lines 34-210; test at `/users/<user>/dev/bc/bunker/repos/web-frontend/animation/mina/tests/state_animator_test.rs`
> 
> **description**: `stateanimator` is a state machine that maps `state` enum values to `timeline` instances. when `set_state()` is called:
> 1. the new timeline's 0% keyframe is overridden with the current animated values via `start_with()`.
> 2. the animation duration resets to zero.
> 3. on each `advance()`, the timeline interpolates from where the previous animation left off toward the new timeline's target.
> 4. if the new state has no timeline, the previous animation is **paused** (not reset) and resumes when the original state returns.
> 
> this creates seamless transitions: a button at 60% hover animation that gets clicked will smoothly blend from its current visual state into the pressed animation, rather than snapping.
> 
> **key code snippet** (the transition logic in `set_state`):
> ```rust
> fn set_state(&mut self, state: &state) {
>  if state == &self.current_state { return; }
>  match self.paused_animation.as_ref() {
>  some((paused_state, paused_position)) if state == paused_state => {
>  self.state_duration = *paused_position; // resume from paused position
>  }
>  _ => {
>  // ... pause tracking logic ...
>  self.blend_next_timeline(state); // calls start_with(&current_values)
>  self.state_duration = duration::zero;
>  }
>  }
>  self.current_state = state.clone();
> }
> ```
> 
> **applicability to plev**: plev has no concept of animation states or transition blending. in a ui engine, buttons have idle/hover/pressed/disabled states, each with different animations. currently this would require manual management. a `stateanimator` pattern would integrate well with plev's signal system and component lifecycle (mount/update/unmount in `component.rs`).
> 
> **decision**: **adapt** -- the full mina stateanimator (with enummap, proc macros, mergedtimeline) is too heavy for plev's minimal-dependency philosophy. but the core pattern of "state -> timeline + blend-on-transition" should be extracted into a lightweight `animationstate<s, t>` that maps states to tweens or keyframesequences and handles blending on state change.

> ## pattern 1: lazy activation via three-handler protocol
> 
> **source**: accesskit `common/src/lib.rs` lines 2882-2931, `platforms/winit/src/lib.rs` lines 81-265
> 
> **description**: accesskit uses three handler traits to manage the full lifecycle: `activationhandler` (called when a screen reader connects), `actionhandler` (routes at actions back to the app), and `deactivationhandler` (called when the screen reader disconnects). the key insight is **lazy activation** -- the application does zero accessibility work until a screen reader actually connects, at which point `activationhandler::request_initial_tree()` is called. this can return the tree synchronously (ideal) or `none` to defer (the adapter provides a placeholder).

> **key code snippet** (accesskit common):
> ```rust
> pub trait activationhandler {
>  fn request_initial_tree(&mut self) -> option<treeupdate>;
> }
> pub trait actionhandler {
>  fn do_action(&mut self, request: actionrequest);
> }
> pub trait deactivationhandler {
>  fn deactivate_accessibility(&mut self);
> }
> ```

> ```rust

>  match event {
>  accesskit_winit::windowevent::initialtreerequested => {
>  egui_winit.egui_ctx().enable_accesskit();
>  eventresult::repaintnow(window_id) // force immediate repaint to build tree

>  accesskit_winit::windowevent::actionrequested(request) => {
>  egui_winit.on_accesskit_action_request(request.clone());
>  eventresult::repaintnext(window_id)
>  }
>  accesskit_winit::windowevent::accessibilitydeactivated => {

>  }

> - `scenenode::rect` with no interaction -> `role::genericcontainer` or skip
> - `scenenode::text` -> `role::label` (static) or `role::textinput` (editable)
> - textinput component -> `role::textinput` with `set_value()`, `set_placeholder()`
> - button-like views (clickable hit regions) -> `role::button`
> - plev's `computedbounds` from layout -> `accesskit::rect` directly
> 
> **decision**: **adapt**. plev should derive bounds from `computedbounds` (layout) or from `hitregion` data, not from scenenode (which is gpu-facing). the mapping should live in the view/component layer, not the compositor layer. a trait like `accessibleview` with `fn accessibility_role(&self) -> option<accesskit::role>` and `fn accessibility_label(&self) -> option<&str>` would be cleaner than egui's enum-matching approach.

> ## pattern 4: id mapping -- internal id to accesskit nodeid
> 
> **source**: egui `crates/egui/src/id.rs` lines 82-84
> 
> **description**: egui's `id` is a `nonzerou64` (hash-based). accesskit's `nodeid` wraps a `u64`. the conversion is trivial: `fn accesskit_id(&self) -> accesskit::nodeid { self.value().into() }`. the root id is a well-known constant: `id::new("accesskit_root")`. this direct mapping avoids any lookup table between framework ids and accessibility ids.
> 
> **key code snippet**:
> ```rust
> pub(crate) fn accesskit_id(&self) -> accesskit::nodeid {
>  self.value().into() // u64 -> nodeid
> }
> 
> pub fn accesskit_root_id() -> id {
>  id::new("accesskit_root")
> }
> ```
> 
> **applicability to plev**: plev's `viewid` is `pub struct viewid(pub u32)`. this needs widening to `u64` for accesskit, or a simple cast. since plev uses `viewid` as a monotonically increasing counter (via `next_view_id()`), there's no collision risk -- just `nodeid(view_id.0 as u64)`. the root should be a reserved id (e.g., `nodeid(u64::max)` or `nodeid(0)` if viewid starts at 1).
> 
> **decision**: **adopt**. direct cast from `viewid(u32)` to `nodeid(u64)`. reserve `nodeid(0)` as the root/window node. no lookup table needed.

> ## pattern 5: focus routing via actionrequest
> 
> **source**: egui `crates/egui/src/memory/mod.rs` lines 565-606
> 
> **description**: when an assistive technology asks to focus a specific node, it sends `actionrequest { action: action::focus, target_node: nodeid }`. egui translates this into its own focus system by storing `id_requested_by_accesskit`. during the next frame, as each focusable widget registers itself, egui checks if the at requested focus on that specific id. if matched, focus is granted and the request is cleared. this bridges at-driven focus with the framework's own keyboard/tab navigation.
> 
> **key code snippet**:
> ```rust
> // during begin_pass, process events:
> if let event::accesskitactionrequest(actionrequest {
>  action: accesskit::action::focus,
>  target, data: none,
> }) = event {
>  self.id_requested_by_accesskit = some(*target);
> }
> 
> // during widget registration:
> fn interested_in_focus(&mut self, id: id) {
>  if self.id_requested_by_accesskit == some(id.accesskit_id()) {
>  self.focused_widget = some(focuswidget::new(id));
>  self.id_requested_by_accesskit = none;
>  self.give_to_next = false;
>  self.reset_focus();
>  }
>  // ... normal tab navigation continues ...
> }
> ```
> 
> **applicability to plev**: plev's `inputstate` already has `focused_view: option<viewid>` and `hit_test_focusable()`. an at focus request would translate to: set `focused_view = some(viewid(target_node.0 as u32))`. plev should also queue the appropriate `inputevent::focus` so the component lifecycle (e.g., textinput blink activation) works normally. this is a thin bridge: `actionrequest -> inputevent`.
> 
> **decision**: **adopt**. map `action::focus(target)` to `input.focused_view = some(viewid::from(target))` plus emit a synthetic `inputevent::focus`. map `action::click` to a synthetic click at the center of the target's bounds. map `action::setvalue` to text input operations. other actions can be no-ops initially.

> ## pattern 6: null platform adapter for unsupported targets (wasm)
> 
> **source**: accesskit `platforms/winit/src/platform_impl/null.rs` (entire file, 24 lines), `platforms/winit/src/platform_impl/mod.rs`

> **key code snippet**:

> pub struct adapter;

>  pub fn new(...) -> self { self {} }

> **applicability to plev**: plev targets 6 platforms. macos (nsaccessibility), windows (uia), linux (at-spi) have native at support. android has talkback. ios has voiceover. wasm currently has no native bridge (future aria potential). accesskit already covers all of these except wasm (where it uses the null adapter) and android (which has an `android.rs` adapter). plev can rely on accesskit's compile-time platform dispatch without any additional branching.
